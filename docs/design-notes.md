# 设计说明：五个决定，和它们的代价

> 这份文档不解释"怎么用"（那是 README 的事），只解释**为什么这么写**，以及**哪些地方我故意没做**。
> 写给要改这份代码的人，也写给要判断我水平的人。

---

## 决定一：为什么把 LLM 和渲染拆成两段

**做法**：模型只输出 JSON，Python 只读 JSON 渲染 HTML。

**为什么**：早期我让模型直接生成 HTML，遇到三个问题：
1. 每次版式都不同，改一处样式要重跑一次模型
2. 模型会"顺手优化"我定的结构，导致下游解析不稳
3. 调试时无法区分"是模型写错了"还是"我的模板错了"

**代价**：多了一层数据契约（`data.json` 的字段必须稳定）。字段一改，历史项目全部要迁移。
**换来**：换剧本只替换数据，渲染器一行不动——这一条在真实改稿里省的时间最多。

---

## 决定二：景别为什么用固定顺序，而不是排序后输出

`SIZE_ORDER = ["大远景","远景","全景","中景","近景","特写"]`

**为什么**：如果按字典序或出现频次排，条形图每次的顺序都不一样，读者无法比较两个项目。
**代价**：出现这 6 档之外的值时，落不到正确位置——目前一律归入 `wide` 兜底。
**这是一个明确的取舍**：宁可新值显示得不精确，也不要图表顺序漂移。

---

## 决定三：为什么"无台词"要用 `（无）` 占位，而不是留空

**为什么**：渲染器要靠这个判断"本片有没有对白"。
- 全部镜头都有台词 → 渲染台词块
- 有 `（无）` → 这部分渲染成"无台词"，且不预留空行

**代价**：输入时必须严格写 `（无）`，写"无"或"-"会判断错。
**为什么不做模糊匹配**：模糊匹配会把"无"字开头的台词（比如"无所谓的……"）误判成无台词。**宁可要求输入规范，也不要猜。**

---

## 决定四：为什么镜号必须是连续的整数

**为什么**：每个镜头卡片有锚点 `#shot-01`，顶部索引也按镜号跳转。
镜号不连续时，索引和锚点会对不上——读者点"03"跳到第 5 镜。

**我没做的事**：不做自动纠正（比如自动重编号）。
**为什么不做**：自动重编号会掩盖输入错误。剧本里的镜号通常有业务含义（比如分镜稿里的场次编号），工具没有资格悄悄改它。
**现在的行为**：不连续就照原样渲染，错位由使用者自己发现。——这是一个**已知缺陷**，我选择暴露它而不是掩盖它。

---

## 决定五：为什么用 Python 标准库，不引入任何依赖

**为什么**：
1. 这份代码的使用者是制片/美术，不是开发者——**他们最可能没有配好 Python 环境**。零依赖意味着 `python build_storyboard.py 项目名` 就能跑
2. 渲染是确定性任务，不需要模板引擎或图像库
3. 376 行能读完，改起来不需要理解框架

**代价**：没有 Jinja 那样的模板继承，HTML 是字符串拼接的。新增一个区块要小心转义（所有用户输入都过 `html.escape`）。

---

## 明确没做的事（以及为什么）

| 没做 | 原因 |
|---|---|
| 不生成图片、不调 Midjourney API | 一旦接生成，就要处理失败重试、配额、版权——那是另一个系统。这份工具只到"提示词"为止 |
| 不做 PDF / PPT 导出 | 要交付就给 HTML 加打印样式，不值得为格式维护两套渲染 |
| 不做分镜合理性判断 | 工具能保证"不丢信息、排版一致"，**不能保证"这条打脸够不够爽"**。判断必须留给人 |
| 不做多语言 | 台词本来就是中英对照写在数据里的，界面语言不是瓶颈 |
| 不做 Web 服务 | 单文件 HTML 双击就开，省掉部署、端口、防火墙三个坑 |

---

## 一句话

这份代码的设计原则只有一条：**确定性的部分写成代码，需要判断的部分留给人。**

所以它拒绝让模型直接排版、拒绝自动纠正镜号、拒绝判断镜头好坏——
每一条"不做"，都是为了不让工具替人做它没资格做的判断。
